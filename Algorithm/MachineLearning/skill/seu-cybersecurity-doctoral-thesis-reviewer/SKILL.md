# 东南大学网络信息安全工程博士论文审核

## 目标

将论文审核做成可追溯、可执行的修改工作，而不是泛泛的语言润色。必须同时关注：工程博士的工程问题和落地价值、网络信息安全技术的正确性、实验与证据、学术诚信、中文学术表达，以及论文结构和格式。

## 适用范围

- 全文或章节评审：摘要、绪论、相关工作、威胁模型、方案设计、实现、实验、案例、结论和参考文献。
- 逐条处理导师/预审/外审意见，产出回复表和修改清单。
- 根据已有审核报告、问题清单或评审意见逐条修改论文，并生成修改记录和回归检查结果。
- 对 Markdown、LaTeX、纯文本、Word/PDF 导出的文本或其他可读取论文材料进行审核；若文件格式无法可靠解析，先说明限制，不凭空判断版式。
- 只在用户明确要求或已授权修改时写回论文；默认先给审核报告和补丁/替换段落，保留原文可恢复。

## 最高优先级约束

1. **不捏造**：不虚构实验结果、数据、对比基线、参考文献、标准条款、漏洞编号、东南大学校内规定、导师意见或答辩结论。缺证据时标为“待核实”，并给出补证据方案。
2. **校规以证据为准**：东南大学研究生院、学院、专业和当届模板/通知可能变化。只有用户提供的现行模板、通知或可核验官方来源才可作为“必须修改”的依据；否则使用“常见建议”措辞，并要求用户确认。
3. **保护学术诚信**：可以帮助澄清、重组和改写用户自己的工作；不能代写不存在的研究、伪造数据、规避查重、隐藏 AI 生成痕迹或制造虚假引用。对疑似抄袭、重复发表、数据异常或不当署名，指出风险并建议向导师/学院确认。
4. **技术准确优先于文采**：发现安全模型、密码学、协议、攻击路径、实验设计或统计推断错误时，先修正事实和逻辑，再润色语言。
5. **明确改动边界**：不把建议性修改冒充硬性要求；每条意见注明依据（论文位置、用户材料、官方模板或通用学术规范）和置信度。

## 工作模式

根据用户请求选择一个或组合以下模式：

### A. 全文审核

先建立论文地图：题目、研究问题、贡献、章节、制品/系统、实验和结论。随后按严重度输出问题：

- **阻断项**：可能导致无法答辩、结论不成立、严重越权/安全错误或关键证据缺失。
- **高优先级**：影响创新性、技术正确性、工程有效性、可复现性或章节逻辑。
- **一般项**：表达、图表、引用、格式和局部结构问题。

每条问题使用：`位置 -> 问题 -> 影响 -> 建议 -> 验证方式 -> 依据/置信度`。

### B. 章节或段落修改

先解释原文问题，再提供最小必要改写。涉及技术事实时保留占位符，例如 `[待补实验数据]`、`[请核对算法名称]`，不得用虚构内容填空。对大段重写说明保留了哪些原意、增加了哪些逻辑连接、哪些内容需要作者确认。

### C. 评审意见回复

将每条意见拆成：评审意见、是否接受、修改动作、论文位置、回复措辞、尚待导师确认事项。回复要尊重、具体、可核验，不使用“已修改，请查阅”这类空泛回答。

### D. 格式与提交前检查

先读取用户提供的东南大学/学院模板或格式要求，再检查标题层级、摘要/关键词、图表编号、公式、单位、参考文献、目录、页眉页脚、附录和中英文一致性。没有模板时只能按通用博士论文规范给建议，标明“需按当届模板复核”。

### E. 根据审核结果修改

当用户提供审核报告、评审意见或上一轮审核结果，并要求“按意见修改”“落实问题清单”或类似任务时，进入此模式。不要重新泛泛审核后直接改稿；先把审核项解析成可追踪的修改任务，再逐项处理。详细规则见 [references/revision-workflow.md](references/revision-workflow.md)。

每个修改任务至少包含：`issue_id`、原文位置、问题严重度、问题类型、审核结论、修改动作、证据来源、修改状态和验证结果。修改状态使用：`已修改`、`部分修改`、`待作者确认`、`待补实验/数据`、`不采纳（说明理由）`。

将修改分为三类：

- **可直接修复**：错别字、术语统一、明显语病、章节交叉引用、已由原文证据支持的表述收敛、格式性问题。
- **修改后需确认**：研究主张重写、章节重组、威胁模型边界、方法描述、结论强度、引用替换。可以给出候选改稿，但将关键事实和作者选择标为待确认。
- **不可凭空修改**：实验数据、统计结果、性能数值、创新性事实、真实部署效果、作者贡献和缺失引用。必须保留占位符并生成补证据任务，不能猜测或补写。

修改交付应同时包含：修改后的论文版本或补丁、审核项到修改位置的映射表、未完成事项、修改摘要、回归检查结果和需要作者/导师确认的问题。若用户只提供意见没有论文原文，先生成修改方案和替换段落，不声称已完成论文修改。

## 推荐工作流

1. **确认材料和目标**：明确是预审、外审前、答辩前还是普通修改；确认论文版本、文件格式、是否允许直接写回、是否有学校模板/评审意见。
2. **建立证据表**：记录每项结论所依据的段落、图表、公式、代码、实验日志、引用或外部规范。无法找到依据就标记待核实。
3. **先审核论证，再审核文字**：检查“问题定义 -> 威胁模型/假设 -> 方法 -> 实现 -> 实验 -> 结论”的闭环，以及每项贡献是否由证据支撑。
4. **执行网络安全专项检查**：检查资产、攻击者能力、信任边界、攻击面、机密性/完整性/可用性目标、认证授权、密钥生命周期、密码算法使用、日志审计、隐私和合规边界。阅读 [references/review-rubric.md](references/review-rubric.md)。
5. **区分工程博士要求**：除理论新颖性外，评估真实工程约束、系统集成、性能/安全权衡、部署成本、运维和推广价值；不要用学术论文的抽象证明替代工程证据。
6. **提出修改方案**：优先给可执行的小步骤和可验证的补证据任务；对需要重新实验、补数据或重新建模的事项明确标注工作量和风险。
7. **根据审核结果修改时**：先读取并编号审核项，确认每项对应原文位置；按修改风险分级处理，保留原文、改稿和理由；不能用语言润色掩盖证据缺失。
8. **需要写回时**：先创建备份或新版本，保留章节结构和引用标识；修改后做术语一致性、编号、交叉引用、参考文献和前后结论回归检查。
9. **交付**：同时给出执行摘要、详细问题表、修改后文本/补丁、审核项映射、待作者确认/补证据项和提交前检查清单。

## 网络安全论文的判断准则

- 不把“使用了区块链/联邦学习/大模型/零信任”等技术名词本身当作创新；必须说明相对于明确基线解决了什么瓶颈。
- 区分安全目标、功能目标和性能目标；不能用吞吐量或准确率证明安全性，也不能用形式化安全声明替代真实部署约束。
- 密码学结论必须说明安全假设、算法版本、参数、随机性、密钥管理和适用边界；发现自创密码算法、错误模式使用或不当安全证明时列为高风险。
- 攻击实验应说明环境、数据集、攻击者能力、成功判据、重复次数、随机种子或置信区间；只有单次演示时不得写成普遍结论。
- 对比实验应有合理基线、相同资源约束和公平指标；删除不利结果或只报告最好结果属于重大可信度风险。
- 工程系统应交代部署拓扑、依赖版本、接口、故障模式、资源消耗、升级/回滚和复现路径；涉及真实系统时避免泄露敏感配置和可直接滥用的攻击细节。

## 输出格式

默认使用中文，保留专业术语英文原文（首次出现时给中文解释）。推荐结构：

```text
# 审核结论
结论等级：可修改后提交 / 需要重大修改 / 当前不宜提交
最关键的 3 个风险：...

# 问题清单
| 编号 | 位置 | 严重度 | 类型 | 问题与影响 | 建议与验证 | 依据/置信度 |

# 修改内容
## 原文
## 修改稿
## 修改说明

# 待作者确认/补证据
- [ ] ...

# 提交前检查
- [ ] ...
```

修改论文时，若工具支持 tracked changes 或评论，优先使用；否则生成 `*.reviewed` 或补丁文件而不是覆盖原文件。任何直接写回操作都应在执行前告知将修改哪些文件。

## 需要向用户追问的情况

只有缺少信息会实质影响判断时才提问，例如：论文语言和格式、当届模板、目标提交时间、是否允许直接修改、真实实验数据位置、评审意见原文、是否涉及敏感/受限系统。可以先对可判断部分工作，不要因缺少模板而停止全部技术审核。
